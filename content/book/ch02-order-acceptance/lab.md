## 实验：订单生命周期与重试

用纸笔或复制下表，模拟 `BUY 0.01 @ 60,000`，假设依次成交 0.004、0.003，再撤销剩余量。本教学接口以账户与 client order ID 为创建幂等键，保存原参数摘要；真实接口须查其 ID 保留期和重试保证。

| 步骤 | 服务端事件 / 客户端观察 | 累计成交 z | 活动余量 l | 已撤销量 c | 服务端状态 | 客户端能否确定？ |
|---|---|---:|---:|---:|---|---|
| 1 | 接受 K-17，分配 O-17；创建响应丢失 |  |  |  |  |  |
| 2 | 第一笔成交 0.004；推送到达 |  |  |  |  |  |
| 3 | 同一 K-17、原参数重试 |  |  |  |  |  |
| 4 | 第二笔成交 0.003；推送延迟 |  |  |  |  |  |
| 5 | 撤销余量；带版本与累计数量的结果到达 |  |  |  |  |  |
| 6 | 第 4 步成交推送迟到 |  |  |  |  |  |

在服务端已接受订单的各行检查 `q=z+l+c`。讨论：同一 ID 改参数、换 ID 用原参数会分别怎样？如何接收迟到的有效成交，同时防止旧订单状态覆盖终态？

最后交换第 4、5 步的服务端生效顺序，重算数量。说明为什么客户端收到撤单成功不能据此把仓位设为零。

## 逐级提示

<details><summary>提示 1：先记录服务端事实</summary>

先忽略客户端看到了什么。每次接受、成交、撤销后只更新 `z、l、c`，再填客户端列。

</details>
<details><summary>提示 2：迟到的是事实还是旧状态？</summary>

一笔此前未登记的 Fill 仍需按 ID 收录；旧版本的订单快照不能覆盖更高版本的终态。

</details>

## 参考解答

<details><summary>展开生命周期表与竞争路径</summary>

| 步骤 | z / BTC | l / BTC | c / BTC | 服务端状态 | 客户端可确认范围 |
|---|---:|---:|---:|---|---|
| 1 | 0 | 0.010 | 0 | 已接受 | 响应丢失，仅知请求超时 |
| 2 | 0.004 | 0.006 | 0 | 部分成交 | 确认这一笔成交；不凭缺少推送排除其他成交 |
| 3 | 0.004 | 0.006 | 0 | 部分成交 | K-17 仍对应 O-17；原 ACK 与当前状态分别解释 |
| 4 | 0.007 | 0.003 | 0 | 部分成交 | 第二笔未到，客户端视图可能仍停留在步骤 2 |
| 5 | 0.007 | 0 | 0.003 | 已撤销余量 | 带版本结果确认终态及累计成交 0.007 |
| 6 | 0.007 | 0 | 0.003 | 已撤销余量 | 收录第二笔 Fill，但不再次增加已从权威累计量恢复的数量 |

每行都满足 `0.010=z+l+c`。订单快照提供累计结果，成交历史提供逐笔解释；两者不能当成两份不同成交相加。

同一 K-17 改参数应报冲突；K-18 用原参数属于新命令，可能再创建一单。创建重试、撤单重试与 Fill 去重各有自己的业务作用域。

若撤单先于第二笔成交生效，结果改为 `z=0.004、l=0、c=0.006`，第二笔不能再使用该订单余量。仓位仍是多头 0.004 BTC。撤单终态描述订单余量，不消除已成交仓位。

</details>

### 掌握检查的答题依据

回忆题应分清“想做什么、接受了什么、现在怎样、已经发生什么”；推导题须写数量守恒；应用题同时给出创建键与成交键；重建图应包含超时后的原单查询与重复事实去重。只写“重试一次”不足以证明正确性。
