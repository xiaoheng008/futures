# 问题：行情越剧烈，订单越多，系统就该一直接单吗？

BTC-USDT 在一分钟内快速波动，Alice 不断改价撤单；其他用户也在下单，行情客户端同时重连。若 API 网关、风险检查、撮合和 WebSocket 推送都堆进同一条无界队列，服务看起来仍在“接收请求”，但用户得到的成交和风险结果会越来越晚。

本章只解决一个问题：**系统接近容量边界时，怎样让拒绝有边界、已接受的状态仍然可信？**容量数字是教学假设；公开交易所的配额只说明客户端 API 契约，不揭示其内部部署拓扑。

# 例子一：用队列算出“继续接收”的代价

先看一个单撮合分区。假设它每秒最多处理 `10,000` 条有效订单命令，突发期间每秒到达 `12,000` 条：

1. 每秒净积压 `12,000 - 10,000 = 2,000` 条。
2. 30 秒后队列积压约 `2,000 × 30 = 60,000` 条。
3. 若高峰后输入降到 `8,000` 条/秒，处理能力只多出 `2,000` 条/秒，清空队列约需 30 秒。
4. 积压期间新请求即使最终处理成功，也可能已经错过客户端时限；旧撤单和新订单还可能在过时状态上继续排队。

这是确定性的小模型，不含网络、磁盘、风险计算和多分区倾斜。它只证明一件事：**队列不是容量；没有上限的排队会把过载变成延迟和不可预测性。**

```mermaid

  I[请求速率 12000/s] --> Q[有界准入队列]
  Q --> M[分区处理能力 10000/s]
  Q -->|队列满或请求过期| R[明确拒绝并返回可重试信息]
  M --> S[持久化订单与成交事实]
  S --> P[账户与行情推送]
```

# 例子二：先区分谁在争用哪一种容量

同一账户快速修改 BTC、ETH 两个永续订单，背后至少有几种不同的争用范围：

1. **入口预算**：IP、API Key、用户或子账户的请求配额，保护网关和鉴权服务。
2. **产品预算**：单个合约的订单命令进入同一撮合顺序，保护该产品的撮合分区。
3. **账户风险预算**：多个产品可能共享抵押品；风险预留必须覆盖账户共同风险，不能只按单一产品并行放行。
4. **推送预算**：一个热门市场的行情广播会扇出到许多连接，不能让慢客户端拖住撮合和账本写入。

因而“按市场分区”可以让单个市场拥有清晰顺序，但它不会自动解决全仓保证金或组合风险。一个参考设计是让撮合按产品维持顺序，让账户风险预留通过独立的账户级版本/原子额度边界串行化或可靠并发控制，再把公开行情扇出放进可降级的异步链路。

# 公开 API 限速说明什么？

主流交易所公开配额采用的维度和反馈方式并不相同：

- Binance USDⓈ-M 文档分别定义 `REQUEST_WEIGHT` 与 `ORDERS` 限额；Binance 的另一份衍生品 API 通用说明明确写出超限时返回 `429`、提供已用权重响应头和重试等待信息。它们说明的是公开 API 契约，不代表内部服务限流实现。[USDⓈ-M 限额定义](https://developers.binance.com/zh-CN/docs/products/derivatives-trading-usds-futures/common-definition)；[Portfolio Margin Pro 通用限流说明](https://developers.binance.com/en/docs/products/derivatives-trading-portfolio-margin-pro/general-info)
- Bybit 文档同时列出 IP 级 HTTP 限制与按 UID/时间窗划分的 API 限制，并为请求返回剩余配额和重置时间等头字段。[Bybit Rate Limit Rules](https://bybit-exchange.github.io/docs/v5/rate-limit)
- OKX 将许多交易相关的 REST 与 WebSocket 请求共享限额，并按 User ID、Instrument ID 等规则区分操作类别。[OKX API Rate Limits](https://app.okx.com/docs-v5/en/#overview-rate-limits)

这些是会变化的客户端契约，应在调用时查阅最新文档；它们不表示交易所内部服务如何限流。本书的内部方案只借此推出：限额键必须对应实际共享资源，客户端错误也要说明何时、在哪个范围可以重试。

# 例子三：把过载变成受控准入

假设 Alice 的 API Key 同时发出 500 个创建单请求，系统检测到该用户额度已用尽，但市场撮合分区仍正常：

1. 在昂贵的风险计算或撮合排队之前，网关按明确的身份键检查配额。
2. 配额不足时立即返回限速拒因、作用域和建议重试时间；不能让请求先进入撮合队列再超时。
3. 每个撮合分区使用有上限的队列，并为等待时间设置 deadline；超过 deadline 的未接受命令直接拒绝。
4. 对已接受订单，状态事实写入之后再确认接受；不能因队列拥塞而返回一个实际上未持久化的“成功”。
5. 慢行情客户端可以丢弃旧的可重建快照或要求重新同步，但成交事实、账本分录和私有订单状态不能静默丢失。

配额策略需防止单一大户、单个热门合约或慢消费者占满共享资源。按用户限额保护公平性，按产品限额保护局部撮合，按账户风险限额保护资金不变量；三者不能互相替代。批量订单还必须按实际包含的订单数量计量，不能把一次 HTTP 请求误当成一次撮合工作。

# 降级顺序：保护事实与风险不变量

下面是教学用的降级框架。实际优先级要由产品规则、监管要求和服务依赖共同确认：

1. 保证已经产生的成交事实、账本写入和强平执行结果可持久化、可恢复。
2. 对新开风险的订单进行准入限流；拒绝要发生在承诺接受之前。
3. 撤单、只减仓请求和风险处置要有明确容量预算及失败路径，不能让高优先级请求无限挤占其他必要工作。
4. 非权威的行情聚合、历史查询、展示刷新可采样、降频或短时关闭，并明确标注数据陈旧。
5. 服务恢复后按序号补发或快照重同步；绝不把“重新连上”当作“所有事件均已送达”的证明。

过载拒绝不是系统失效；接受后失去命令或错记资产，才是核心正确性失败。无论限流器怎样扩展，都不得破坏订单数量守恒、成交幂等、账本可重放和风险额度原子预留。

# 容量观测：别只盯 CPU

至少按产品分区、账户风险域和事件流监控：

- 命令端到端延迟的 p50/p95/p99、超时数和各类拒绝原因；
- 队列深度、最老消息等待时间、分区倾斜与处理吞吐；
- 风险检查耗时、预留冲突/重试、订单簿撮合耗时；
- Fill 到账本、账本到账户投影、投影到私有推送的事件滞后；
- WebSocket 慢消费者数、序号缺口、重同步频率和被丢弃的可重建行情量；
- 账本/仓位对账差异。此类正确性指标必须告警，即使 CPU 很低也不能忽略。

容量测试应按真实请求混合、单市场热点、账户跨市场共享风险、行情扇出和断线重连突发进行；只做均匀流量压测容易漏掉最危险的热点和队列堆积。

# 掌握检查

- **回忆**：入口预算、产品撮合预算、账户风险预算和推送预算分别保护哪种资源？
- **推导**：到达率 `15,000/s`、处理率 `11,000/s`、突发 `20 s`，计算新增积压；流量恢复到 `9,000/s` 后，计算理想清空时间。
- **应用**：单一账户跨 BTC、ETH 两市场共享全仓抵押品，两个请求并发通过本地产品限流；指出仍需哪个账户级保护边界。
- **重建**：从队列不断增长推导有界准入、按资源域限流、过载拒绝、可降级推送与事实/账本正确性监控。
