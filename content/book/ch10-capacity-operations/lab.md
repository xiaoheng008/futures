## 场景

一个 BTC-USDT 撮合分区持续处理 `10,000` 条订单命令/秒。压力测试给出三个阶段：

| 阶段 | 到达率 | 持续时间 |
|---|---:|---:|
| 平稳期 | 8,000 条/秒 | 5 分钟 |
| 突发期 | 12,000 条/秒 | 30 秒 |
| 恢复期 | 8,000 条/秒 | 2 分钟 |

起始队列为 0。忽略单条命令大小和处理耗时差异，暂不考虑扩容。

## 第一步：手算队列

1. 平稳期结束时有多少积压？
2. 突发期结束时队列有多长？
3. 恢复期需要多久才能清空突发积压？
4. 突发期最后一条命令最少会在队列中等待多少时间？这个估值忽略了哪些真实成本？

## 第二步：定义入口策略

先将队列容量限制为 `20,000`，满时在接受之前拒绝新请求。重新计算突发期间接受量、拒绝量、结束积压和恢复耗时；区分队列等待估值与真实端到端延迟。

为每一类请求填充表格。不要只写“限流”：

| 请求 | 限流键 | 是否排队 | 队列/等待上限 | 超限响应 | 观测指标 |
|---|---|---|---|---|---|
| 新开仓订单 |  |  |  |  |  |
| 撤单 |  |  |  |  |  |
| 只减仓订单 |  |  |  |  |  |
| 公共行情订阅 |  |  |  |  |  |
| 私有账户事件 |  |  |  |  |  |

说明为什么 IP、用户、产品和账户风险域需要不同的限流键。指出哪个限额必须覆盖跨产品共享保证金。

## 第三步：注入故障

在 30 秒突发的第 15 秒，让账本消费滞后 5 秒；同时，50% 行情客户端断线并立即重连。决定系统如何：

- 限制新订单准入；
- 处理撤单、减仓和强平请求；
- 给慢行情客户端降级并恢复序号连续性；
- 保证 Fill 已产生但用户推送延迟时，用户仍能查询权威订单/成交状态。

## 第四步：通过条件

列出至少四个量化或可判定的验收条件。必须包含一个延迟/队列指标、一个明确拒绝条件、一个成交或账本正确性不变量，以及一个推送恢复条件。

## 参考解答

<details><summary>展开队列计算与一种可评审的策略</summary>

第一步无界模型：平稳期积压 0；突发结束 `2,000×30=60,000`；恢复清空需要 `60,000/2,000=30 秒`；末尾请求的理想 FIFO 等待约 `60,000/10,000=6 秒`。本题连续流近似忽略离散边界、服务时长差异、风险检查、磁盘、网络和下游延迟。

20,000 上限模型：10 秒填满，随后 20 秒每秒拒绝 2,000；总接纳入队 320,000、拒绝 40,000、处理 300,000、积压 20,000，恢复 10 秒，理想最大排队估值约 2 秒。`接纳入队-处理=积压变化`，`到达=接纳入队+容量拒绝`。

下面是一套自造预算示例，数值仅用于给设计提供可判定边界，不能直接当作生产配置：

| 请求 | 限流键 | 排队与上限 | 超限结果 | 观测指标 |
|---|---|---|---|---|
| 新开仓 | IP/API Key + UID + 产品；另做账户风险原子预留 | 分区总队列≤20,000，未接受等待≤2秒 | 接受前明确拒绝 | 接受/拒绝数、最老等待、预留冲突 |
| 撤单 | UID + 产品，独立准入预算 | 总容量内预留2,000槽，等待目标≤0.5秒 | 明确未接受；按原单查询/重试 | 撤单确认延迟、未知结果数 |
| 只减仓 | UID + 产品 + position scope | 与风险请求共用总容量内保留2,000槽 | 明确拒绝或待确认；不放大旧数量 | 在途减仓量、仓位版本冲突 |
| 公共订阅 | IP + 连接 + 频道 | 每连接缓存≤1MB或≤1秒消息 | 降频/断开并要求新快照 | 缓存、慢连接、缺口 |
| 私有账户事件 | account_id + 连接 | 可重发事实持久化；实时连接缓存≤1MB | 断开提示查询/恢复，不删除权威事件 | 事件滞后、游标、恢复差异 |

预留槽属于总队列容量，不能再加到 20,000 上突破上限。优先级只在明确准入/调度边界生效，已进入撮合日志的顺序不能任意插队；上述等待目标仍需压测，不能由保留槽自动保证。跨产品共享保证金必须由账户风险域覆盖。

账本滞后 5 秒时，监控持久待处理工作量与最老年龄，收紧新风险准入；给撤单、减仓和风险处置保留有界预算，但这些请求若产生新 Fill 也需要账本容量。不能无限接受“高优先级”请求。重连使用退避加随机抖动，限制快照并发与每用户恢复速率；公共簿可重建，Fill 和账本义务不可丢弃。

一种验收约定：总队列不超过 20,000；队列满且未接受时返回可辨识拒绝；同一 Fill 每账户每用途恰好一个金额效果，订单数量守恒；恢复客户端的快照/增量前驱连续且账户差异清零。不确定操作返回查询依据，不能误报确定失败。延迟目标按实测 p99 与负载条件报告。

正文掌握检查的 15,000/11,000 场景：20 秒增加 80,000；恢复 9,000 后净清理 2,000/s，清空需 40 秒。

</details>
