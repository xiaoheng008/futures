# 场景

一个 BTC-USDT 撮合分区持续处理 `10,000` 条订单命令/秒。压力测试给出三个阶段：

| 阶段 | 到达率 | 持续时间 |
|---|---:|---:|
| 平稳期 | 8,000 条/秒 | 5 分钟 |
| 突发期 | 12,000 条/秒 | 30 秒 |
| 恢复期 | 8,000 条/秒 | 2 分钟 |

起始队列为 0。忽略单条命令大小和处理耗时差异，暂不考虑扩容。

# 第一步：手算队列

1. 平稳期结束时有多少积压？
2. 突发期结束时队列有多长？
3. 恢复期需要多久才能清空突发积压？
4. 突发期最后一条命令最少会在队列中等待多少时间？这个估值忽略了哪些真实成本？

# 第二步：定义入口策略

为每一类请求填充表格。不要只写“限流”：

| 请求 | 限流键 | 是否排队 | 队列/等待上限 | 超限响应 | 观测指标 |
|---|---|---|---|---|---|
| 新开仓订单 |  |  |  |  |  |
| 撤单 |  |  |  |  |  |
| 只减仓订单 |  |  |  |  |  |
| 公共行情订阅 |  |  |  |  |  |
| 私有账户事件 |  |  |  |  |  |

说明为什么 IP、用户、产品和账户风险域需要不同的限流键。指出哪个限额必须覆盖跨产品共享保证金。

# 第三步：注入故障

在 30 秒突发的第 15 秒，让账本消费滞后 5 秒；同时，50% 行情客户端断线并立即重连。决定系统如何：

- 限制新订单准入；
- 处理撤单、减仓和强平请求；
- 给慢行情客户端降级并恢复序号连续性；
- 保证 Fill 已产生但用户推送延迟时，用户仍能查询权威订单/成交状态。

# 第四步：通过条件

列出至少四个量化或可判定的验收条件。必须包含一个延迟/队列指标、一个明确拒绝条件、一个成交或账本正确性不变量，以及一个推送恢复条件。
