## 实验目标

从下列产品和用户输入开始，独立构造订单、成交、风险、故障恢复与容量保护模型。所有参数只用于本实验，不代表真实交易所规格。

## 第一轮：重建正常交易

产品参数：`BTC-USDT` 线性永续、`tickSize=0.1`、`qtyStep=0.001`。Alice 有 `1,000 USDT`，提交 `BUY 0.01 @ 60,000 GTC`。卖盘为 `0.004 @ 59,999` 和 `0.006 @ 60,000`。初始保证金率 10%，手续费与资金费先忽略。

完成表格：

| 阶段 | 状态/事件 | 数量或金额 | 必须成立的不变量 |
|---|---|---|---|
| 收到请求 |  |  |  |
| 校验规格 |  |  |  |
| 风险预留 |  |  |  |
| 第一笔成交 |  |  |  |
| 第二笔成交 |  |  |  |
| 账本与仓位 |  |  |  |

计算名义价值、两笔成交的加权平均价、初始保证金，以及订单 `CumQty` 和 `LeavesQty` 在每次成交后的值。

## 第二轮：推导风险处置

沿用第一轮的仓位与保证金，假设维持保证金率固定为 0.5%，忽略风险档位和费用：

1. 在 Mark=`54,000` 时分别算未实现盈亏、逐仓权益和维持要求，判断风险边界。
2. 若强平实际在 `53,950` 成交，算实际平仓盈亏和相对 60 USDT 保证金的差额。
3. 写出从风险触发到成交、账本、仓位归零和缺口处置的事件顺序。
4. 将 Mark 改为 `55,000`，说明风险状态如何变化；指出若加入费率、资金费和阶梯档位，需要哪些额外输入。

## 第三轮：注入重复与崩溃

先把第二笔卖盘改为 `0.003 BTC`，并在两笔成交之后撤销剩余委托。重算累计成交、撤销量和仓位，再删除客户端第一笔成交推送：说明客户端需要哪些权威查询才能重建。明确写出终态数量如何守恒，不能把撤销订单当成撤销仓位。

任选一个 Fill，设计其唯一业务 ID 和账本幂等键。然后选择下面一个故障点：

- Fill 持久化前撮合进程崩溃；
- Fill 已持久化、账本未提交时账本服务崩溃；
- 账本已提交、确认游标未更新时消息重复；
- 私有事件已提交、WebSocket 推送丢失。

画出恢复流程，标记权威事实、重放起点、可能重复的位置、对账方式和最终对用户可见的状态。

## 第四轮：注入断线与过载

公共订单簿增量序号为 `100、101、103`；同一时刻入口流量高于撮合容量 20%。说明：

- 客户端何时必须废弃本地簿并重新取快照？
- 系统在哪一步拒绝新订单，如何区分“被拒绝”和“已接受但结果未知”？
- 哪些已发生的订单/成交事实不能被丢弃？哪些行情数据可以降级并重建？
- 如何保证新开仓限流不会绕过账户级保证金预留？

## 第五轮：交付你的重建

提交一张包含规格、入口、风险预留、撮合、Fill、账本、价格/风险、强平、恢复、推送和限流的图；再提交正常路径事件表、故障恢复表和不变量清单。

同伴评审时任选一个节点注入超时、重试或版本变化。作者需要沿图指出受影响的状态、唯一事实、恢复路径和可能需要重新计算的量。

## 参考解答

<details><summary>展开正常交易、风险与故障重建</summary>

第一轮：

| 阶段 | 结果 | 不变量 |
|---|---|---|
| 收到请求 | 稳定创建键 K-17，BUY 0.01 @ 60,000 | 同键参数一致，不重复创建 |
| 校验规格 | 600,000 ticks、10 lots，限价名义价值600 USDT | 整除、单位、正数、规格版本 |
| 风险预留 | 60 USDT，可靠交接后接受 | 同账户原子预留、失败可补偿 |
| 第一笔成交 | F-1：0.004 @ 59,999；CumQty=0.004、LeavesQty=0.006 | 独立 Fill ID，0.01=0.004+0.006 |
| 第二笔成交 | F-2：0.006 @ 60,000；CumQty=0.010、LeavesQty=0 | 0.01=0.01+0，订单 FILLED |
| 账户与仓位 | 钱包1,000；多仓0.01，均价59,999.6；逐仓分配60 | 开仓无600本金转移；事实幂等 |

实际开仓名义价值为 599.996 USDT；订单限价名义价值是 600。按实际成交价值严格乘 10% 会得 59.9996，但本题明确 M 固定 60，不能混用两个分配假设。

第二轮：Mark 54,000 时 UPL=-59.996、E=0.004、MM=2.7，触发。本章全平执行 53,950 实现 -60.496，超过 M 的 0.496 为待处置缺口。Mark 55,000 时 UPL=-49.996、E=10.004、MM=2.75，未触发。费用、资金费、档位改变时，需要对应规则版本、余额分录、参与仓位、价格、扣减额与舍入规则。

第三轮独立重置第一轮：成交 0.004+0.003=0.007，撤销0.003，活动余量0，多仓0.007，均价约59,999.428571。按实际成交名义价值×10%的自造转换策略，第一笔成交后持仓占用23.9996、挂单预留36，释放价差对应额度0.0004；第二笔后持仓占用41.9996、挂单预留18；撤单只释放18，不能再释放已经处理过的0.0004。若规则选择逐仓固定分配42，则保留42、只释放18。两种策略应先声明，不能在一个状态表中混用。

缺第一笔推送时查询原订单累计量、成交历史与账户/仓位版本；不能把已恢复累计量与迟到 Fill 再相加。

| 故障点 | 权威依据 | 恢复与验收 |
|---|---|---|
| Fill 持久化前崩溃 | 已提交命令/撮合前缀 | 按固定规则恢复；未提交 Fill 不可对外确认 |
| Fill 已持久、账本未提交 | Fill ID 和日志序号 | 从账户确认水位续读，原子提交效果键与分录 |
| 已提交、确认游标未推进 | 分录和已处理键 | 重投效果为0，再推进水位；账本/仓位各自核验 |
| 持久私有事件推送丢失 | outbox/事件日志与对象查询 | 重发或补查，客户端去重并与权威状态对账 |

第四轮：本例 seq 只按教学加一协议，101之后收到103就停止可信使用、取新快照并衔接缓存；真实 API 按前驱/区间规则。入口到达为服务率的1.2倍，积压净增长0.2倍服务率；先设置有界准入，接受前拒绝，接受后未知结果提供查询。已接受命令、Fill、分录不可静默丢弃；公共行情可在标明不可信后重建。每笔通过容量检查的创建仍需账户原子风险预留。

</details>

### 最终重建的评审表

| 要交付的证据 | 通过条件 |
|---|---|
| 正常路径事件表 | 单位、版本、数量守恒、金额来源可复算 |
| 故障恢复表 | 每个崩溃点有权威依据、幂等键、水位与对账目标 |
| 端到端图 | 每条箭头能说明持久化、重复与超时责任 |
| 风险与清算表 | Mark判定与实际执行损益分开，缺口归属有记录 |
| 过载与推送策略 | 未接受拒绝明确；已接受可恢复；客户端缺口可检测 |

多种架构可以通过评审；评分依据是边界与不变量，不是是否画出与正文完全相同的服务框图。
