# 问题

客户端接收订单簿增量时短暂断线。继续应用新到消息会不会让本地簿看起来正常、实际已失真？

# 发现

客户端需要明确快照版本、增量序号、缓冲策略和重同步条件。用户私有流还要处理登录过期、重复事件、订阅恢复，以及 REST 查询与实时推送之间的竞态。交易所对外公开的协议可说明字段与客户端责任，但不披露内部事件总线拓扑。

# 实验

参考 Bybit 快照/增量语义，模拟在序号 n 与 n+2 间丢失 n+1。设计客户端何时丢弃本地簿并重新取快照。[订单簿文档](https://bybit-exchange.github.io/docs/v5/websocket/public/orderbook)

# 新问题

断线重连会让很多客户端同时重新订阅和取快照。服务怎样在过载时保住撮合和账户正确性？

# 重建

从一个缺失的增量推出序号、缓冲、检测和重同步协议。
