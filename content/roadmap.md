# 学习路线与写作状态

本书面向有后端开发基础的读者，目标是从合约规格和订单输入出发，逐步推导出可以解释成交、账务、风险、强平与故障恢复的参考系统。课程按因果依赖组织，不声称复刻任何交易所内部实现。

## 已完成工作初稿

以下章节已有正文与配套实验。**“初稿”表示内容已写出，不代表已完成技术审校或出版定稿。**

1. 合约规格、单位和版本
2. 订单接受、幂等与生命周期
3. 价格优先、时间优先和订单簿
4. 成交、账本与仓位投影
5. 保证金检查和并发额度预留
6. Last、Index、Mark 与资金费率
7. 强平、破产价、保险基金和 ADL
8. 事件重放、快照与对账
9. WebSocket 快照/增量与断线恢复

## 计划编写

### 高峰期系统如何保护核心状态？

# 问题

行情波动带来下单激增、撤单风暴和 WebSocket 扇出增长。所有请求都继续接受，能否保证低延迟？

# 发现

容量压力迫使系统明确优先级、限流维度、背压和过载拒绝策略。撮合按市场分区有利于局部顺序，却使跨市场组合风险、共享抵押品和全局清算更复杂。指标需覆盖端到端延迟、队列积压、拒单原因、事件滞后和账务差异，而不只看 CPU。

# 实验

给出固定处理能力与突发流量，比较无界队列、按用户限流、按市场限流及优先级队列。评价尾延迟和订单结果可预测性。

# 新问题

架构全了，怎样从原始需求重新导出它，而不是背诵模块名？进入最终重建。

# 重建

按“正确性优先、过载仍可解释”的要求，画出入口、撮合、账本、风控和推送的隔离边界。

### 从空白重建合约交易核心

# 起点

你只知道：用户希望提交带杠杆的买卖委托，交易所要公平撮合并在损失扩大前管理风险。请在不看前文的情况下，从一张纸开始推导所需能力。

# 重建挑战

1. 定义合约参数、订单输入和拒单原因。
2. 画出订单状态，并保持数量守恒。
3. 从公平匹配需求推出订单簿与撮合规则。
4. 从成交事实推出账本、仓位和幂等边界。
5. 从潜在亏损推出初始/维持保证金检查。
6. 区分价格用途并推导永续资金费结算需要。
7. 设计强平缺口处理及恢复、对账路径。
8. 定义 API 接受确认与 WebSocket 状态推送契约。
9. 加入限流、故障注入和监控，说明优先保护哪些不变量。

# 评估

每项按四个层次自评：能讲明白（回忆）、能推导关键式子（推导）、能处理新情境（应用）、能从基础问题重建关系（重建）。章节完成不代表掌握；若重建卡住，返回触发该抽象的压力重新尝试。
